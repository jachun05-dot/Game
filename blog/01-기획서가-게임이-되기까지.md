# [DDD 개발기 #1] 기획서가 게임이 되기까지 — 그리드를 버리고 텍스트로

[그림: 타이틀 화면 — 숏소드를 든 열여섯 살 소년]

## 열여섯 살만 들어갈 수 있는 미궁

작은 섬의 영지에 미궁이 하나 있어요. 미궁 깊은 곳, 차원문 너머에 마법 셉터가 잠들어 있다는 소문이 돌아요. 그런데 셉터의 마법 때문에 미궁에는 **열여섯 살 인간만** 들어갈 수 있어요.

영주는 아이들에게 조건을 겁니다. 셉터를 찾으면 바칠 것, 그리고 **매달 세금을 낼 것.** 못 내면 처형이에요.

제가 만들고 있는 게임 **DDD — 열여섯 살, 미궁으로**는 이 설정에서 시작했어요. 한 번 죽으면 끝인 로그라이크이고, 죽은 방식에 따라 다음 삶에서 섬길 수 있는 "옛 신"이 열려요. 굶어 죽으면 기아의 신, 함정에 죽으면 재앙의 신, 세금을 못 내 처형되면 탐욕과 채무의 신이요.

## 처음 기획은 그리드 로그라이크였다

8월에 처음 쓴 기획서는 지금과 꽤 달랐어요.

- 칸 단위로 한 칸씩 움직이는 **턴제 던전 크롤**(DCSS 같은)
- 시야 3칸, 전장의 안개, 50×50 타일 맵 자동 생성
- 섹터 10개, 섹터마다 3층
- Unity로 마을 화면과 1섹터 시험판까지 만들었어요

기획서는 400줄이 넘었어요. 부위별 부상(머리가 결손되면 즉사), 정신 상태이상 조합, 포만감과 피로도… 하고 싶은 게 너무 많았죠.

[그림: 초기 기획서의 섹터 10개 표 또는 그리드 웹 데모 화면]

## 10월 13일, 장르를 바꿨다

다시 작업을 시작한 날, 가장 먼저 한 결정이 **"그리드를 버리고 텍스트 게임으로 간다"**였어요.

참고한 건 이런 게임들이에요.

- 이번 생은 야구다
- 벤치에서 발롱까지
- 80억 분의 1

공통점은 **글과 숫자 카드로 한 사람의 인생을 빠르게 굴린다**는 거예요. 매 턴 결과가 카드로 나오고, 쌓인 선택이 성장으로 이어지죠.

이 게임에 필요한 건 한 칸씩 걷는 손맛이 아니라, **"이번 달에 무엇을 하고, 미궁에서 어디까지 내려갈지"** 정하는 판단이라고 생각했어요. 그리드는 그 판단을 늦게 만들 뿐이었어요.

## 버린 것과 남긴 것

| 버린 것 | 남긴 것 |
|---|---|
| 한 칸씩 이동, 시야, 타일 맵 | 세계관(섬·미궁·셉터·영주) |
| 직접 조작하는 전투 | 매달 세금, 못 내면 처형 |
| Unity | 죽음으로 여는 신앙 |
| | 능력치 6개, 주사위(d20) 판정 |
| | 부위별 부상, 포만감·피로도 |

대신 이렇게 바꿨어요.

- **마을은 1주 = 1턴.** 1~3주차에는 훈련·탐문·외부 탐험·여관 중 하나를 고르고, 4주차에 미궁에 들어가요.
- **미궁은 방 단위.** 방과 방이 이어진 지도를 한 방씩 나아가요. 옆방은 "???"로 보이고 감각 판정에 성공하면 미리 알 수 있어요.
- **전투는 완전 자동.** 플레이어는 "HP가 몇 % 이하면 물약을 마신다", "언제 도망친다" 같은 방침만 정해요.
- **죽으면 묘비 카드.** 이름, 살아남은 달 수, 죽은 이유, 그리고 해금된 신이 남아요.

[그림: 마을 화면 — 이번 주 할 일]

## 기술 스택: 서버 없는 웹 게임

Unity를 내려놓고 고른 건 웹이에요. 링크 하나로 바로 열리고, 휴대폰에서도 돌아가니까요.

| 용도 | 고른 것 |
|---|---|
| 언어 | TypeScript |
| 화면 | React 18 |
| 빌드 | Vite |
| 테스트 | Vitest |
| 시뮬레이션 스크립트 | Bun |
| 저장 | 브라우저 localStorage (서버 없음) |
| 배포 | GitHub Pages |

## 로직 먼저, 화면은 나중에

가장 신경 쓴 건 **게임 규칙과 화면을 완전히 떼어 놓는 것**이었어요.

```
src/
  game/   ← 규칙: 전투, 미궁, 마을, 신앙 (React를 전혀 모름)
  ui/     ← 화면: 규칙을 불러서 그리기만 함
```

실제로 첫 커밋은 화면 없이 **게임 로직과 봇뿐**이었어요(설정 파일까지 약 1,800줄). 화면(약 3,800줄)은 그다음 커밋에 붙였고요.

게임의 모든 진행은 "행동(Action)" 하나를 받아 다음 상태를 돌려주는 함수 하나로 통해요.

```ts
export type Action =
  | { t: "activity"; a: Activity }   // 이번 주 할 일
  | { t: "train"; training: string; free: [StatKey, StatKey] }
  | { t: "move"; room: number }      // 미궁에서 다음 방으로
  | { t: "potion" }
  // …

export function act(prev: GameState, a: Action): GameState {
  const s = structuredClone(prev); // 이전 상태는 건드리지 않는다
  apply(s, a);
  return s;
}
```

화면은 버튼을 누르면 `act(state, action)`을 부르고, 돌아온 상태를 그리기만 해요. 저장도 이 상태를 통째로 JSON으로 넣어 두면 끝이고요.

## 같은 시드면 같은 인생

로그라이크라 난수가 많은데, 난수 생성기 상태도 게임 상태 안에 숫자 하나로 넣었어요(mulberry32).

```ts
export function nextFloat(st: RngState): number {
  st.s = (st.s + 0x6d2b79f5) | 0;
  let t = st.s;
  t = Math.imul(t ^ (t >>> 15), t | 1);
  t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
}
```

그래서 **같은 시드 + 같은 선택이면 항상 같은 결과**가 나와요. 버그를 재현할 때도, 밸런스를 비교할 때도 이게 큰 힘이 됐어요.

## 첫날 끝에 남은 것

장르를 바꾼 그날 안에, 처음부터 끝까지 한 바퀴 도는 버전이 돌아갔어요. 웹 브라우저에서 바로 열리는 게임이에요.

그리고 첫 밸런스 목표도 정했어요.

> 첫 달에 약 30%가 죽고, 1년 안에 1섹터를 깨는 사람은 약 40%.

이 숫자를 어떻게 맞췄는지는 3화에서 이야기할게요. 힌트를 드리면, 규칙이 화면과 떨어져 있으니 **사람 대신 수천 판을 플레이하는 봇**을 같은 `apply()` 함수로 돌릴 수 있었어요.

다음 화에서는 이 게임의 심장인 **"죽어야 열리는 신"** 이야기를 할게요.
